# Test audit

Use three modes with one value bar:

- **Authoring:** evaluate every new or changed test before adding it.
- **Audit:** review a focused set of tests for weak assertions, duplicate coverage, implementation coupling, and unnecessary test-only production seams.
- **Campaign:** review a subsystem's complete test surface. Read [the campaign procedure](<skills/test-audit/CAMPAIGN.md>) before starting.

Optimize for confidence, not deletion count. Keep broad audits in coherent, separately reviewable changes.

## Establish repository context

Read applicable repository and scoped contributor instructions first. Discover the languages, build tools, test frameworks, test locations, continuous integration (CI) routing, and review requirements from repository documentation and configuration. Do not assume a directory layout, package manager, runner, default branch, or hosting platform.

Identify the **production owner**: the component responsible for the behavior. Its **owner boundary** is the interface where a test can observe that behavior independently of internal implementation. A **test-only production seam** is an export, flag, wrapper, or injection hook used only to make internals accessible to tests.

Use existing repository tools. Do not install tooling or start external services merely to follow this skill. State missing prerequisites and validation limits. Audit mode starts with read-only discovery; report evidence before editing. If the user requests review only, do not edit.

## Authoring gate

Before adding a test, answer these questions. If an answer is missing, do not add the test yet.

1. What observable behavior, invariant, or independent contract does it protect?
2. What credible regression makes it fail?
3. Why does existing coverage not already catch that failure? Give each contract one primary test owner at the strongest practical boundary. Another layer needs a distinct risk, such as a transport or lifecycle failure that the primary owner cannot reach. Prefer extending parameterized cases or shared fixtures over near-duplicate tests. Consolidate duplicated setup in the same change.
4. Does it require a test-only production seam? If so, first move the test to the real boundary. If that is impractical, justify the seam against a concrete contract and the repository's testing conventions. Do not treat a genuine dependency boundary as unnecessary merely because tests use it.

Check the test against every pattern below. A match fails the gate unless the retention bar identifies an independent contract. If behavior-preserving refactoring breaks the test, rewrite it at the owner boundary unless the implementation constraint is itself a documented contract.

For a bug regression, demonstrate that the test fails on the pre-fix code for the intended reason and passes after the repair. If you cannot run that control, state the limitation; do not claim the regression is proven. Do not replay the same bug at every layer without a distinct failure mode.

## Low-value patterns

Use this checklist for authoring and discovery. A match is a candidate for investigation, not automatic permission to delete.

- Assertion-free coverage probes with no meaningful failure condition.
- Self-comparisons and tests that merely copy inputs to expected outputs.
- Copied fixtures, inventories, manifests, or export lists without an independent contract.
- Exact source, import, or string searches tied to implementation spelling.
- Private predicate or call-shape tests duplicated at real boundaries.
- Duplicate invocations of the same contract.
- Adapter-local replays of shared helper behavior.
- Tests that only preserve test-only exports, globals, or wrappers.
- Production code whose only callers are tests, after checking indirect and external use.
- Expected values generated by the same helper or renderer under test.
- Mocks that implement the asserted behavior, or one identical mock standing in for different interfaces.
- Fixtures that supply the result or callback ordering the production owner should produce.
- Persistence assertions against a store the production path never writes.
- Capability tests that restate flags rather than exercise the promised behavior.
- Negative controls that pass for an unrelated reason, such as another guard rejecting the input first.
- Test names or fixtures that promise more than the assertions exercise.

## Value and retention bar

Tests justify maintenance cost by protecting behavior, a credible regression, or an independently meaningful contract. Refactoring sensitivity is evidence of coupling, not proof that a test is disposable.

Before judging a candidate, read the complete test, production owner, entry points, callers, callees, sibling implementations, overlapping tests, CI routing, and relevant history. When a claim depends on a dependency, inspect its source, interface definitions, or authoritative contract documentation. Record unavailable evidence instead of assuming it supports deletion.

Keep tests that independently enforce public APIs, extension interfaces, protocols, configuration, migrations, storage, security, platform behavior, defaults, exact-byte output, generated cross-language interfaces, packaging, releases, or architecture constraints. Also keep:

- Call ordering when order is observable behavior.
- Regressions with a credible failure mode.
- Source inspection when it is the cheapest independent guard of a real contract and survives unrelated identifier refactoring.
- Tests that fail on the baseline until the failure is understood. A failure may expose a product defect, environment issue, or test defect; it is not a deletion reason.

Static analysis, execution cost, or implementation-like appearance alone does not justify removal. Prove that an independent contract remains protected before deleting its test.

## Discovery and candidate evidence

Group discovery by actual production ownership: for example, core libraries, integrations, applications, and tooling. Add a cross-cutting pattern pass when useful. Use parallel discovery only when available and authorized; otherwise inspect the groups sequentially. Outside campaign mode, prefer a few high-confidence candidates over a speculative inventory.

Record every field before editing a deletion candidate:

- Exact test name and location.
- Failure the test can actually detect.
- Non-test callers of the production or support seam, including indirect and external consumers where applicable.
- Stronger remaining owner-boundary proof, or evidence that no contract needs protection.
- Relevant history and the reason the test or seam exists.
- Production or test-support deletion enabled, or “none.”
- Risk and the focused validation command.

If required evidence is missing, retain the candidate pending investigation.

## Edit shape

Choose one coherent owner-boundary batch. Remove obsolete test-only seams and dead production paths only after checking their consumers and compatibility requirements. Do not preserve unnecessary aliases. Move retained regressions to their canonical owners, and consolidate repeated dependency or package assertions into one shared contract where appropriate.

Prefer simpler production code over test-driven indirection. Do not add replacement tests that restate the same implementation. Do not convert uncertain candidates into cleanup to increase deletion counts.

## Validation

Do not edit files while a test, build, or analysis run depends on those files in the same checkout. Coordinate concurrent work or use isolated checkouts. Before running integration or live tests, check their credentials, services, cost, and external side effects; obtain authorization when required.

1. Run the repository's smallest relevant owner and sibling suites with its documented runner and filters.
2. For removed source searches or plan assertions, run the executable behavior, contract check, or safe dry-run that proves the real contract.
3. Run targeted formatting and static checks. In a Git repository, run `git diff --check`; otherwise use the available patch or whitespace check.
4. Run the repository's required affected-component checks. If no change-routing tool exists, derive scope from dependencies and CI configuration. Record the commands and rationale.
5. Run broader suites when the risk or repository policy requires them. State skipped or blocked checks and their consequences.
6. Inspect the final diff. In Git, use `git diff --numstat` to report production/tooling changes separately from tests and test support; use equivalent diff statistics elsewhere.
7. Complete the repository's required review process. Check that removed coverage still has independent proof.

## Landing and continuation

Commit, push, create a review request, or merge only when authorized. Follow the repository's contribution workflow rather than assuming a particular script or platform. Land one coherent change at a time. Before starting another batch, refresh the baseline using the repository's branch policy and repeat read-only discovery.

## Handoff

Report:

- Causes and removed low-value categories.
- Production owner simplifications.
- Retained false positives and their contracts.
- Focused and broader validation actually run, with results and limitations.
- Production/tooling versus test/support line changes.
- Review and merge state, if applicable.
- Named follow-ups.
