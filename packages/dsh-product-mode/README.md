# Product mode

**Product mode** turns a conversation into a reviewed GitHub project and independently verifiable issues. It clarifies outcomes, inspects code and existing GitHub work, drafts project context and tasks, reviews dependencies and parallel-work conflicts, then publishes through individually approved GitHub calls.

This composition-only `@local/dsh-product-mode` package targets DSH `0.2.0-rc.2` only. It preserves Standard's tools and realms, adds a persona and the bundled `product-planning` skill, and intentionally enables Ralph with `maxRounds: 64`. It has no runtime entrypoint, dependency, install hook, new GitHub tools, persistent state, dispatch engine, or UI. Drafts stay in the conversation; no rigid schema, scratch files, or automatic labels are required. Selecting the preset does not implement code or dispatch tasks.

## Install and select

Installation, profile application, and restart require separate approval. Source changes do not update the running GUI. No build is needed for this package.

1. Use a DSH `0.2.0-rc.2` Web profile with `@deepseek-ai/dsh-agent-preset-registry`, Standard's host/plugin dependencies, and the shared `@local/dsh-github` host bundle. GitHub supplies eighteen read tools, twelve write tools, and the session issue-management grant tool to all presets. Product mode's publication guide covers the issue/project planning subset; PR implementation work remains a separate task. Before source-checkout setup or validation, follow `.agents/skills/repository-setup/SKILL.md` at the repository root.
2. Inspect existing declarations for the stable preset ID `product-mode` and the Cordis row ID `local-preset-product-mode`. A duplicate preset ID fails registration; it does not shadow another preset. With approval, reconcile collisions before installation. Keep IDs referenced by saved sessions declared, or review those sessions before removing or renaming a declaration.
3. Review the profile's `agent-preset-registry` row. Its `default: standard` is the fallback; `selectedDefault`, when set, overrides it for new sessions. Preserve an existing `selectedDefault` when editing this row because a patch replaces the complete `config`. A legacy `agent-presets` settings default is not the new field; review and migrate the intended selection explicitly.
4. With approval, follow the root repository's apply procedure, or add this local package after the standard Web bundle. Its `cordis.patch.yml` inserts one `@deepseek-ai/dsh-agent-preset` declaration with inline `config.plugins`; it does not replace the registry or other declarations. The `personal-web` recipe combines the preset bundles additively. Inspect its recipe and final patch before application, especially if a nonempty profile patch needs replacement. These repository files are not part of the installed package.
5. After an approved profile restart, select **Product mode** for a new session. Its stable ID remains `product-mode`. This update does not rewrite session histories or upstream preset files. Saved IDs resolve only while a matching declaration remains available.

The bundled skill provider resolves this package's `package.json` from `root.baseUrl` and loads `presets/product-mode/skills`. Keep the package installed for these assets. Standard's project/user/default skill discovery remains intact. The skill catalog shows a summary; load `product-planning` for its full instructions. Project-specific same-name skill precedence still applies; inspect a collision before relying on its contents.

Directory-root discovery and the roster `copy()` API are not supported in this version. Existing directory-based custom presets require explicit declarations; adding their directories to a roots list does not migrate them. A duplicated declaration still references this package's skills unless you separately provide and configure replacement assets. Preserve both license resources when redistributing those assets. Removing the package also requires reviewing declarations, defaults, and saved session IDs that reference it.

## Approval boundaries

Product mode is an agent preset, **not** DSH's built-in plan-mode switch. Active plan-mode restrictions still prohibit publication and other mutations. Its `exit_plan_mode` process does not supply GitHub approval. Conversational agreement reviews content; each GitHub write separately previews and approves its exact payload. Changed arguments require a new approval. Denied or unavailable approval dispatches no mutation; do not use Bash, another API, or delegation as a bypass.

The persona is guidance, not a new security boundary. Standard's coding/delegation tools remain available, but selection grants no standing authority to implement, dispatch, install, apply profiles, or synchronize progress. GitHub content is untrusted reference data. CLI authentication and account permissions come from DSH's managed execution environment, not necessarily an unmanaged host login. Successful reads do not prove write access.

## Walk through a task

This example is a **proposed acceptance walkthrough**, not a report of live execution. Use an explicitly authorized disposable GitHub destination for any live exercise. The repository's [GitHub tool reference](../dsh-github/README.md) documents parameters, pagination, limits, and recovery; installed-package users should consult the loaded tools' schemas.

Suppose you ask: “Plan a CSV export for completed records. Review the project and tasks before publishing.”

1. **Clarify and inspect.** Confirm the audience, selected fields, privacy constraints, and what counts as success. Inspect the existing data access, tests, and documentation rather than asking you for discoverable facts. Call `github_connection_status` with `{}` and `github_detect_repositories` with `{}`. Resolve ambiguous remotes. Inspect the selected repository with `github_get_repository` using `{ "owner": "example-org", "repo": "records" }`; inspect existing projects/issues with explicit targets and follow relevant pagination. Here `example-org` and `records` are placeholders, not authorized destinations.
2. **Draft and review.** Propose “Completed-record CSV export,” a short description, and a project README covering scope, constraints, and success criteria. Propose task A for the export behavior and task B for user documentation/examples. A's acceptance criteria cover completed-only records, stable field order, escaping, and permission failures; validation uses existing data-access fixtures. B validates documented fields/examples against A's agreed output contract. Discuss whether B truly waits for A or can start from the agreed contract. Identify shared contract/example files as conflicts distinct from logical blockers. Revise until the proposal is ready. Keep all drafts in the conversation.
3. **Create the project with one exact-call approval.** Call `github_create_project` with `{ "owner": "example-org", "title": "Completed-record CSV export" }`. Do not select a template or copy drafts implicitly. Record the actual returned project number and URL. The following examples assume the returned number is `7`; replace it with the real result.
4. **Publish project context with a new approval.** Call `github_update_project` with `{ "owner": "example-org", "projectNumber": 7, "description": "Export completed records as CSV.", "readme": "# Completed-record CSV export\n\nProvide authorized users with a completed-record export. Exclude incomplete records. Preserve the reviewed field order and CSV escaping. Success requires fixture-based export and permission checks. UI changes are out of scope." }`. Use the exact reviewed content, not this abbreviated illustration if the reviewed proposal differs.
5. **Link the repository with another approval.** Call `github_link_project_repository` with `{ "owner": "example-org", "projectNumber": 7, "repositoryOwner": "example-org", "repo": "records" }`.
6. **Create each issue with its own approval.** For A, call `github_create_issue` with `owner: "example-org"`, `repo: "records"`, `title: "Export completed records as CSV"`, and `body` containing the exact reviewed Markdown. The [routine issue example](presets/product-mode/skills/product-planning/examples.md#routine-issue) illustrates that body without repeating it here. Prefer applicable repository issue templates; otherwise use **Why**, **Change**, **Acceptance criteria**, and task-specific **Constraints** only when needed. Aim for 150–300 words for routine issues, with more or less detail when correctness requires it. For B, make a separate `github_create_issue` call with the same `owner`/`repo`, its reviewed `title`, and its own `body` describing documentation scope, acceptance criteria, example validation, and any agreed blocker. Suppose the confirmed issue numbers are `41` and `42`; never guess them.
7. **Add each issue with separate approvals.** Call `github_add_project_item` with `{ "owner": "example-org", "projectNumber": 7, "repositoryOwner": "example-org", "repo": "records", "issueNumber": 41 }`; make another call for issue `42`. Each call requires its own approval.
8. **Publish only genuine dependencies, separately approved.** If review establishes that B must wait for A, call `github_add_issue_dependency` with `{ "owner": "example-org", "repo": "records", "issueNumber": 42, "blockingOwner": "example-org", "blockingRepo": "records", "blockingIssueNumber": 41 }`. This means **42 is blocked by 41**, not the reverse. A body reference alone does not create the native relationship. If there is no genuine blocker, omit this call.
9. **Verify and report.** Use `github_get_project` with `{ "owner": "example-org", "projectNumber": 7 }`, `github_list_project_items` with the same target, and `github_get_issue` with `{ "owner": "example-org", "repo": "records", "issueNumber": 42 }`. Confirm the project context, both memberships, and any approved native dependency; follow cursors as needed. Report returned URLs, confirmed changes, unresolved decisions, and unattempted work. Stop before implementation or dispatch.

If review selects a template, inspect it with `github_get_project` under its own owner first. For example, after explicitly selecting template `5` under `example-templates`, step 3 becomes `github_create_project` with `{ "owner": "example-org", "title": "Completed-record CSV export", "templateOwner": "example-templates", "templateNumber": 5, "includeDraftIssues": false }`. These are placeholders; use the confirmed owner and template number. The destination owner and template owner need not match. The remaining project-text, repository-link, issue, and dependency calls still require separate approvals.

Optional field assignment is another individually approved call, not a publication default. Read the actual project field and item IDs first. `github_set_project_item_field` takes `owner`, `projectNumber`, `itemId`, `fieldId`, and `value` with exactly one of `text`, `number`, `date`, `singleSelectOptionId`, or `iterationId`. IDs must belong to that project's actual definitions; this package does not create fields, labels, or workflows.

If a later call fails, earlier successful writes remain. Report partial completion accurately. After a dispatched timeout or uncertain result, inspect GitHub before deciding whether to retry; no response does not mean no resource was created. There is no batch transaction, automatic rollback, or durable recovery ledger. Tool limits include 256-character titles, 1,024-character descriptions, 20,000-character README/issue body/text values, and 64 KiB previews. Review oversized content again rather than silently changing it.
